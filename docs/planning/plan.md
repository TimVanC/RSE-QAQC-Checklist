# Build plan: RSE QA/QC Production Checklist

Status: proposed, awaiting Tim's approval. No application code exists yet.
Inputs: `PRD_QAQC_Checklist_App.md` v1.0, the workbook analysis in `docs/discovery/`, the verified Housecall Pro
reference in `docs/reference/`, and Ron's go-live email (checklists in use since Mon 2026-07-06; 35 task + 10 callback
tabs per employee per month; submission validates pay).

## 1. Decisions baked into this plan

| Topic | Decision | Why |
|---|---|---|
| Step model | 44 answerable items (34 steps + 10 sub-items), every one mapped to its workbook cell | Full fidelity to the workbook; nothing Ron tracks today is lost |
| Scoring | Computed server-side on every answer save, stored in `checklist_scores`, plus the monthly rollup as a query | PRD section 8; stored rows make the export and the future Operations Manager trivial |
| Callbacks | `type = callback`, linked to the parent via `parent_checklist_id`; excluded from production totals, counted separately | Matches the workbook's `Task1:Task35` rollup |
| Checklist creation | Lazily on first open from the queue; the tracker computes "missing" as jobs without a submitted checklist | No ghost rows; works for jobs that never need a checklist |
| Sync freshness | Webhooks primary, 15-minute reconcile cron, nightly 30-day backfill, manual refresh button | Meets "appears within 30 minutes" even if webhooks are delayed; cron alone meets it if webhooks are never configured |
| Auth | Neon Managed Better Auth, Magic Link plugin with `disable_sign_up: true`; app roles in our own `app_users` table | Invite-only without custom auth code; roles enforced from our DB, not from a token claim |
| Time | All day boundaries computed in `America/New_York` on the server | PRD section 3 |
| ORM | Drizzle with SQL migrations committed under `drizzle/` | PRD allows Drizzle or Prisma; Drizzle is lighter on Vercel functions |
| Tests | Vitest; scoring fixtures generated by Excel itself | Excel is the oracle, not my reading of the formulas |

## 3. Scoring (`src/lib/scoring/`)

```ts
// checklist-score.ts: pure function, one checklist in, one row of checklist_scores out
export interface ChecklistScore {
  service_quote: 0 | 1;      // s02 == 'Y'
  in_progress: 0 | 1;        // s17 == 'Y'
  completed: 0 | 1;          // s34 == 'Y'
  fail_ops_check: 0 | 1;     // s22 == 'Y'
  fail_qaqc: 0 | 1;          // s23 == 'N'
  fail_tool_control: 0 | 1;  // s26 == 'N'
  fail_callback: 0 | 1;      // s31 == 'Y'
  total_failures: number;    // sum of the four flags            (C90)
  failures_value: 0 | 1;     // total_failures > 0 ? 1 : 0       (C91, "Red")
  bottom_line: number;       // completed + count(flags == 0)    (C94, 0..5)
  perfect_task: 0 | 1;       // bottom_line == 5 ? 1 : 0         (C95, "Black")
  completed_marks: number;   // count(any answer == 'Y') + (s22 == 'N') + (s31 == 'N')   (M75)
}
```

Rules carried over from Excel: blank is never N; comparisons are on upper-cased values; `B` never counts as `Y`.

```ts
// rollup.ts: monthly / per-period rollup over TASK checklists only (callbacks excluded, as in the workbook)
total_service_quotes = sum(service_quote)                       // D9
total_completed      = sum(completed)                           // D11
total_in_progress    = sum(in_progress) - total_completed       // D10
approved_pct         = D9 ? (D10 + D11) / D9 * 100 : null       // D14
declined_pct         = D9 ? 100 - approved_pct : null           // D15
in_progress_pct      = D9 ? D10 / D9 * 100 : null               // D16
completed_pct        = D9 ? D11 / D9 * 100 : null               // D17
black                = sum(perfect_task)                        // B20
red                  = sum(failures_value)                      // B21
bottom_line_pct      = (black + red) ? black / (black + red) * 100 : null   // B23
callbacks            = count(checklists where type = callback)  // app-only count
```

Tests: `scripts/workbook/gen_fixtures.py` fills the template with ~60 scenarios (edge cases plus seeded random
answers across all 44 cells), recalculates in Excel, and writes `tests/scoring/fixtures/*.json`
(`{answers, expected: {C81..C95, M75}, monthly: {D9..B23}}`). `checklist-score.test.ts` and `rollup.test.ts`
assert equality. Fixtures are committed so CI does not need Excel.

## 6. Auth and roles

- Neon Managed Better Auth on the dedicated project. Magic Link plugin enabled with `expires_in: 15`, `disable_sign_up: true`.
- `@neondatabase/neon-js` auth client; server helper reads the session (per Neon's Next.js server reference) and joins `app_users` by `auth_user_id` (fallback by email on first login, then stored).
- Invite flow (admin): create `app_users` row, create the Better Auth user through the Admin plugin (random password, never used), send the first magic link. Deactivating sets `active = false` and revokes sessions.
- `requireRole(allowed: Role[])` is the first line of every server action and route handler; `middleware.ts` only checks for a session. Role comes from `app_users`, so a role change takes effect on the next request.
- Email sender: shared Neon SMTP for development; dedicated provider on an RSE domain before go-live (open question 19).

## 7. Housecall Pro sync design (read-only)

### Client (`src/lib/hcp/client.ts`)
- `fetch` wrapper: base `https://api.housecallpro.com`, `Authorization: Token ${HCP_API_KEY}`, `Accept: application/json`, 20 s timeout.
- Retry on 429/5xx/network: 5 attempts, exponential backoff with jitter, honour `RateLimit-Reset` and `Retry-After`. Concurrency 2.
- `paginate(path, params)` async generator over `page`/`page_size` (start at 50; `scripts/verify-hcp.ts` probes the max).
- Logging: counts and HCP ids only, never names/addresses.

### What is pulled
| Entity | Call | Stored in |
|---|---|---|
| Employees | `GET /employees` (all pages) | `technicians` |
| Jobs in window | `GET /jobs?scheduled_start_min&scheduled_start_max&expand[]=appointments&sort_by=updated_at` | `hcp_jobs`, `hcp_customers`, `hcp_job_assignees`, `hcp_appointments` |
| Recently changed jobs | `GET /jobs?sort_by=updated_at&sort_direction=desc` paged until `updated_at < watermark` | same (catches reschedules out of the window, cancellations) |
| Invoices + payments | `GET /jobs/{id}/invoices` for each job touched in this run | `hcp_invoices`, `hcp_payments` (from `invoice.payments[]`) |
| Job types / tags | `GET /job_fields/job_types`, `GET /tags` (nightly) | `app_settings.hcp_catalog` for the project-type mapper and admin exclusions |

### Schedules (`vercel.json`)
| Job | Schedule | Window |
|---|---|---|
| `reconcile` | `*/15 * * * *` | scheduled_start in [today-2d, today+7d] NY, plus updated-since-last-run scan |
| `backfill` | `30 7 * * *` (03:30 New York) | [today-30d, today+30d], employees, catalog |
| `webhook` | on event | the one entity |
| `manual` | button on the queue | the selected day; 1 run/minute/user |

**Decided 2026-10-14:** the Vercel account is on the Hobby plan, which allows only daily crons. `vercel.json`
therefore runs `reconcile` once a day at 01:00 UTC (21:00 New Jersey, before the nightly calls) and `backfill` at
07:30 UTC. Freshness inside the day comes from webhooks and the queue's Refresh button. If Ron wants the 15-minute
cadence without upgrading Vercel, point an external scheduler (for example cron-job.org) at
`GET /api/cron/reconcile` with header `x-cron-secret: <CRON_SECRET>` every 15 minutes; the endpoint accepts that
header as well as Vercel's bearer.

### Webhooks (`/api/webhooks/hcp`)
1. Read the raw body; verify `HMAC_SHA256(HCP_WEBHOOK_SECRET, Api-Timestamp + "." + body)` against `Api-Signature`
   (hex or base64, constant-time); reject if the timestamp is older than 5 minutes.
2. Insert into `webhook_events` with `dedupe_key = sha256(event + entity id + event_occurred_at)`; duplicates return 200.
3. Fetch the entity from the API (`GET /jobs/{id}` with appointments, then its invoices; `GET /customers/{id}`) and upsert.
   The payload is kept for forensics but the API response is the source of truth.
4. Respond 200 within the function budget; failures leave `status = pending`, and the reconcile cron retries pending events (max 5 attempts).
5. Events subscribed: the job, appointment, invoice and customer events listed in `docs/reference/housecall-pro-api.md`.

### Upsert rules
- `insert ... on conflict (hcp_job_id) do update ... where excluded.hcp_updated_at >= hcp_jobs.hcp_updated_at` so an old webhook cannot overwrite newer cron data. Same pattern for invoices/customers. Assignees and appointments are replaced per job inside one transaction.
- `job.deleted` and `job.canceled` set `deleted_at` / `canceled_at`; rows are never physically deleted. The queue hides them but a checklist already started stays reachable from the tracker.
- Every run writes a `sync_runs` row with counts `{jobs, customers, appointments, invoices, payments, employees, errors}`.
- Technicians: upsert from employees; also upsert any `assigned_employees[]` seen on a job so departed staff still resolve.

### Auto-checks (`src/lib/hcp/auto-checks.ts`)
Computed when a checklist is opened and whenever the job is upserted while the checklist is not submitted.
Stored in `checklist_answers.auto_suggested_value` + `auto_evidence`; never overwrites a manual value.

| Step | Suggest | Evidence shown |
|---|---|---|
| 1 | Y if `started_at <= scheduled_start - 30 min`, N if `started_at > scheduled_start`, none otherwise | scheduled start, started at, both in NJ time, with the caveat that HCP records "started", not arrival |
| 10 | Y if another job for the same customer has `scheduled_start > this job's scheduled_start` | that job's number and date |
| 11 | Y if a payment on this job or customer with `paid_at < scheduled_start` and amount >= $100 | payment amount and date |
| 27 | Y if an invoice for the job has `status = paid` and `paid_at <= completed_at + 1 h`; N if invoice is open after completion | invoice number, status, paid at |
| 30 | Y if `completed_at` is set | completed at |
| 33 | set to Y by Submit (source `auto_confirmed`) | submitted by / at |
